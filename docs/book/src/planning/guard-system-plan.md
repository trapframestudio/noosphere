# Guard System

**Status:** plan. Spawned 2026-05-25 from a sim-QA observation that
posted guards feel sparse and the formation_offset ring around a
base center reads as "everyone clustered at one spot" rather than
"NPCs guarding the perimeter."

The fix is structural: replace the implicit "guard the base
center + formation slots" model with **explicit, designer-placeable
guard points**, with sensible defaults generated by the POI baker
so every base gets perimeter coverage without hand-authoring.

## Goals

1. **Designer control.** A level author can drop guard points
   anywhere — on a watchtower, behind sandbags, on a roof — and
   the sim will post guards there.
2. **Auto-generation default.** The POI baker emits a default
   ring of guard points around every `BASE_*` POI so a freshly
   placed base immediately has plausible guard coverage.
3. **Multiple post types per base.** A base can mix:
   - *Static posts* — one NPC sits on each, facing outward.
   - *Perimeter waypoints* — guards walk between them on a loop.
4. **Auto-replacement.** If a posted guard dies, the next eligible
   squad can claim the slot. If a perimeter loop loses a walker,
   another guard fills in.
5. **Capture-aware.** When a base flips faction (via the
   `base_capture` system that already ships), its guard points
   transfer to the new owner. Defenders of the old owner clear out.

## Out of scope (this iteration)

- Smart facing / lookout angles per guard point. Static posts get a
  designer-set yaw; perimeter loops point along the next leg.
  Behavioral facing (turn toward gunshot, scan FOV) lives in
  tactical-AI work.
- Threat-driven repositioning (guard breaks post to take cover
  under fire). Existing `BlackboardUrgency` candidates already
  pull guards into combat; designing a "return to post" behavior
  after combat ends is a follow-up.
- Variable garrison sizes per base. A `BASE_HEADQUARTERS` should
  ideally support 10+ guards across multiple shifts; the baker
  defaults can encode this per `BaseKind` but the sim-side
  scheduler currently assumes one squad per post.

## Approach

Six phases, each landable as its own commit.

### Phase A — `GuardPointMarker3D` authoring node

**Scope.**

- New `godot/scripts/world/guard_point_marker.gd` (`@tool`,
  extends `Marker3D`). Mirrors the existing
  `InteractionAreaMarker3D` pattern.
- Exports:
  - `kind: GuardPointKind` enum: `STATIC` or `PERIMETER`.
  - `loop_id: String` — perimeter waypoints with the same
    `loop_id` form a closed patrol route. Empty for STATIC.
  - `facing_yaw_deg: float = 0.0` — static-post hint; ignored
    for perimeter.
  - `faction: Faction = Faction.NONE` — restricts which faction
    can post here. NONE = any.
  - `radius_m: float = 2.0` — arrival tolerance. NPCs within
    radius count as posted.
- Inspector gizmo: small flag mesh + radius ring, color-tinted
  by faction (reuse `FactionColors`). Group all instances under
  `&"guard_points"` for cheap bridge enumeration.
- Mirrors the placement contract of `PoiMarker3D` /
  `InteractionAreaMarker3D` so designer experience is uniform.

**Files touched.** `godot/scripts/world/guard_point_marker.gd`
(new), `godot/scenes/markers/GuardPointMarker.tscn` (new), the
new `Faction` mirror in `faction-registry-plan.md` style.

### Phase B — Sim-side `GuardPoints` resource

**Scope.**

- New `crates/simn-sim/src/resources.rs`:
  ```rust
  pub struct GuardPoint {
      pub id: String,            // designer-provided or auto
      pub kind: GuardPointKind,  // Static | Perimeter
      pub loop_id: Option<String>,
      pub pos: [f32; 3],
      pub facing_yaw: f32,
      pub faction: Option<FactionId>,
      pub radius_m: f32,
      // Live state
      pub occupant: Option<NpcId>,  // single NPC posted here
      pub claimed_by_group: Option<u64>,
  }

  pub struct GuardPoints {
      pub by_region: HashMap<RegionId, Vec<GuardPoint>>,
      pub by_id: HashMap<String, (RegionId, usize)>,
  }
  ```
  Modeled after `InteractionAreas`.
- New `Sim::register_guard_point(region, point) -> Result<()>`
  API + `Sim::clear_guard_points_for_region(region)`.
- Transient — not serialized. Re-enumerated from the Godot scene
  every region attach (matches `GuardPosts` / `InteractionAreas`
  semantics).

**Files touched.** `crates/simn-sim/src/resources.rs`,
`crates/simn-sim/src/world/mod.rs` (registration +
`#[serde(default)]` for snapshot compat),
`crates/simn-godot/src/sim/mod.rs` (bridge `#[func]`).

### Phase C — `base_spawner.gd` / scene-walker for GuardPoints

**Scope.**

- New `godot/scripts/world/guard_point_spawner.gd`. Same pattern
  as `loot_container_spawner.gd` / `base_spawner.gd`.
- `spawn_guard_points(tree, region_id, sim) -> int` walks
  `&"guard_points"` group, maps GDScript enums to sim strings,
  calls `sim.register_guard_point(...)` per marker.
- Hooked into `test_map.gd::_on_terrain_ready` alongside the
  existing `base_spawner` / interaction-area calls.

**Files touched.** `godot/scripts/world/guard_point_spawner.gd`
(new), `godot/scripts/test_map.gd` (one new call).

### Phase D — POI baker auto-generates default guard points

**Scope.**

- Extend `godot/scripts/tools/poi_baker.gd` so when it spawns a
  `BASE_*` PoiMarker, it also drops a default cluster of
  `GuardPointMarker3D` children under a `GuardPoints/` subnode:
  - **BASE_CHECKPOINT** — 2 static posts flanking the spawn,
    facing outward.
  - **BASE_OUTPOST** — 4 static posts in a square (~15 m
    radius), facing outward.
  - **BASE_SAFEHOUSE** — 1 static post at entrance + 4 perimeter
    waypoints forming a patrol loop (~25 m radius).
  - **BASE_HEADQUARTERS** — 6 static posts in two rings + 6
    perimeter waypoints (~40 m radius outer loop).
  - **BASE_RESEARCH_POST** — 3 static posts.
  - **BASE_CAMP_SITE** — none (campsites are non-faction).
- Y-snap each guard point via the active `TerrainNode` like
  PoiBaker already does for POIs.
- All guard points inherit the parent base's `faction`.
- Existing **Bake POIs** button covers them in the same pass;
  no new inspector controls needed.

**Files touched.** `godot/scripts/tools/poi_baker.gd`.

### Phase E — `build_guard` posts squads to GuardPoints

**Scope.**

- New `crates/simn-sim/src/systems/squad_planner.rs::build_guard`
  signature change: takes `&GuardPoints` and `&mut GuardPoints`
  (via the `posts: ResMut` already in the planner's call shape,
  or a sibling `guard_points: ResMut`).
- For squads picking `ObjKind::Guard`:
  - Find the squad-faction-eligible `GuardPoint`s in the
    squad's region.
  - For **static** points, pick the nearest unclaimed one. Each
    NPC in the squad targets a different post (round-robin
    within the squad). Squad size larger than available posts →
    leftover NPCs roll Wander or take perimeter loops.
  - For **perimeter** points, claim a `loop_id` and have squad
    members walk the loop in formation (one NPC per leg).
- New `SquadObjective::GuardPoint { point_ids: Vec<String>,
  loop_id: Option<String>, expires_at: u64 }` variant —
  replaces / generalizes the legacy `Guard { base_pos, post_key }`.
  Legacy variant stays around for snapshot back-compat; planner
  prefers GuardPoint when available.
- `squad_target` returns the post position for each NPC's
  assigned slot. Perimeter loops cycle waypoints on arrival.
- Death / despawn clears `occupant` so another squad can claim.
- `GUARD_TENURE_TICKS` (the 15-min rotation from prior work)
  still applies — squads vacate the post group and re-roll.

**Files touched.** `crates/simn-sim/src/systems/squad_planner.rs`,
`crates/simn-sim/src/systems/npc_goals.rs` (executor for the
new variant), `crates/simn-sim/src/resources.rs` (SquadObjective
enum).

### Phase F — Capture transfer + walkthrough + iteration plan

**Scope.**

- `base_capture::base_capture_check`: when a base flips, walk
  the `GuardPoints` in radius and:
  - Update each point's `faction` to the new owner.
  - Clear `occupant` / `claimed_by_group` so the new owner's
    squads can claim them.
- Test: spawn a contested test map, watch a hostile squad
  capture a base, verify guard points now accept their faction.
- New walkthrough doc at
  `docs/book/src/walkthroughs/guard-system.md`:
  - How to author guard points by hand.
  - How auto-generation works per `BaseKind`.
  - Static vs perimeter semantics.
  - Capture transfer behavior.
- Iteration plan doc at
  `docs/book/src/planning/sim-iteration-5-15-plan.md` linking
  the six phases.
- Update `docs/book/src/SUMMARY.md` + the planning README index.

## Open questions

- **Static post yaw** vs current `Rotation` ECS contract — does
  the executor force the NPC's `Rotation` to the post's
  `facing_yaw_deg`, or just steer them to position and let
  perception drive look-direction? Recommend force-yaw on
  arrival; perception can override on aggro.
- **Perimeter loop direction** — clockwise or random? Probably
  clockwise from the lowest-id waypoint for determinism. Per-loop
  randomization would feel more natural but break snapshot
  reproducibility.
- **Squad size vs. post count mismatch.** A 5-NPC squad picks an
  outpost with 4 static posts. The 5th NPC takes a perimeter
  point if available, else rolls Wander. Should we let two NPCs
  share a post? Probably not — defeats the "visible guard
  coverage" point.

## Reused existing infra

- **InteractionAreaMarker3D pattern** — guard points are
  structurally identical to interaction areas with capacity 1
  + a `kind` discriminant. The marker → sim resource → bridge
  → squad-planner pipeline is the same.
- **POI baker auto-generation** — same per-`BaseKind`
  per-marker-cluster authoring path that already handles
  base placement.
- **`SquadObjective::Guard`** — the existing variant can be
  deprecated once Phase E lands; perimeter-style Guard becomes
  the default and the simple "stand at base center" path
  remains as a degenerate single-static-post case.
